# cursor-asset-model Specification

## Purpose

Defines ownership and naming of Cursor assets so OpenSpec-generated vendor files stay distinct from future SDD Framework-owned commands, skills, rules, and agents.

## Requirements

### Requirement: Vendor-managed OpenSpec assets
Cursor assets generated by OpenSpec whose names use the `opsx-*` or `openspec-*` prefixes SHALL be treated as vendor-managed. The framework SHALL NOT rename them, SHALL NOT redefine their command semantics, and SHALL NOT mix framework-specific methodology into those files.

#### Scenario: Existing generated commands remain vendor assets
- **WHEN** the repository's `.cursor/commands/` directory is inspected
- **THEN** the OpenSpec-generated `opsx-*` commands remain present under their generated names
- **AND** they are documented as vendor-managed

#### Scenario: Existing generated skills remain vendor assets
- **WHEN** the repository's `.cursor/skills/` directory is inspected
- **THEN** the OpenSpec-generated `openspec-*` skills remain present under their generated names
- **AND** they are documented as vendor-managed

#### Scenario: Vendor semantics are not rewritten
- **WHEN** framework documentation describes the OpenSpec Cursor workflow
- **THEN** it describes the installed `opsx-*` / `openspec-*` surface as OpenSpec-owned
- **AND** it does not present those files as SDD Framework-owned assets

### Requirement: Framework-owned asset namespace
Future SDD Framework-owned Cursor assets SHALL use an explicit `sdd-*` namespace for commands, skills, rules, and agents, and SHALL be distinguishable from vendor OpenSpec assets by that namespace.

#### Scenario: Naming rule is documented
- **WHEN** a contributor plans a framework-owned Cursor asset
- **THEN** documentation requires an `sdd-*` name
- **AND** it forbids placing framework-owned behavior into `opsx-*` or `openspec-*` files

#### Scenario: Absence of custom assets is valid
- **WHEN** the foundation is implemented
- **THEN** the repository MAY contain no `sdd-*` Cursor assets yet
- **AND** the ownership boundary is still documented as authoritative

### Requirement: Ownership boundary without catalog implementation
This capability SHALL define the Cursor asset ownership boundary without requiring implementation of a custom SDD command, skill, rule, or agent catalog.

#### Scenario: Foundation does not add custom Cursor catalog
- **WHEN** the foundation change is applied
- **THEN** no custom `sdd-*` Cursor commands, skills, rules, or agents are required to exist
- **AND** the documented ownership model is sufficient for later changes to add them

### Requirement: Reserved prefixes are exclusive
Cursor asset names that use the `opsx-*`, `openspec-*`, or `sdd-*` prefixes SHALL be reserved. Consuming-project Cursor assets SHALL NOT use those prefixes. Project-specific Cursor extensions SHALL use names outside the reserved set.

#### Scenario: Project assets cannot claim reserved prefixes
- **WHEN** a consuming project adds a local Cursor rule, skill, command, or agent
- **THEN** documentation forbids naming that asset with an `opsx-*`, `openspec-*`, or `sdd-*` prefix
- **AND** it requires a project-specific name outside the reserved set

#### Scenario: Framework namespace stays framework-owned
- **WHEN** a consuming project has received framework `sdd-*` assets into its Cursor context
- **THEN** those names remain framework-owned
- **AND** the project is not permitted to overwrite them with project-specific behavior under the same names

### Requirement: Primitive-matched Cursor paths
When a later change creates a framework-owned Cursor asset, that asset SHALL live in the Cursor path that matches its primitive: rules under `.cursor/rules/`, skills under `.cursor/skills/`, commands under `.cursor/commands/`, and agents under `.cursor/agents/`.

#### Scenario: Planned asset has a matching path
- **WHEN** a contributor plans a framework-owned Cursor asset of a given primitive
- **THEN** documentation requires the corresponding `.cursor/` path for that primitive
- **AND** it does not allow placing that asset under a path belonging to a different primitive
